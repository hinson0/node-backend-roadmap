## 1. 目标

随着 AI 生成代码速度增加，建立三层治理机制，并保留按需专项 Review：

```text
代码产生 → Push / MR Hard Gate → dev
                  ↑              ↓
       高风险变更合并前专项 Review  Daily Map + Weekly Reduce
                                  ↓
                           候选问题 → 人确认
                                  ↓
                           独立修复 / 简化 MR
                                  ↓
                             门禁与复核
```

Hard Gate 阻止其覆盖范围内的确定性错误进入 `dev`；不能保证所有错误都被拦截。
Daily 发现已经合并的遗漏和架构漂移；不能替代合并前检查。
Weekly 汇总、去重和评估简化候选；实际降低复杂度，需要后续改动被接受、实施和验证。
Targeted Review 用于高风险变更，原则上前移到合并前；已合并后发现风险时也可补做。

核心原则：AI Review 提供证据和候选，不自行决定重构，不代替确定性门禁。

## 2. 第一层：Push / MR Hard Gate

这一层继续保持自动化、确定性、快速失败。

不让 AI 在这个阶段主动“重构代码”。

方案要求的主门禁如下；这是治理目标，不代表本次已确认仓库全部实现：

```text
format:check
docs:audit
openapi:check
lint
typecheck
unit test
db:check
db:check-comment
integration
build
smoke-built
```

入口：

```bash
pnpm check
```

CI：

```text
GitLab Pipeline
↓
pnpm check
```

### 这一层应该检查什么

只检查可以明确判定的规则。

例如：

```text
类型错误
Lint
格式
测试失败
数据库 Schema / migration 漂移
数据库字段注释缺失
OpenAPI 漂移
文档结构错误
构建失败
dist 无法运行
```

未来可以逐渐加入一些可以机械判断的 architecture rule。

例如：

```text
packages/ui
禁止依赖 apps/*

packages/contracts
禁止依赖 apps/*

Feature
禁止直接 import 其他 Feature internal file

db/schema.ts
禁止直接定义业务 table

db/schema-comments.ts
禁止直接定义领域 comment
```

但不要把模糊的架构判断塞进 CI。

例如：

```text
这个 Service 是否太复杂？
这个抽象是否值得存在？
这个文件是否应该拆？
```

这些交给 AI Review。

### 合并门禁验收【修订】

不能仅因为存在 `.gitlab-ci.yml` 或 `pnpm check` 就认定门禁有效。需要核验 `dev` 的实际分支保护、禁止未经允许直接 Push、MR 必须有成功的流水线，以及跳过流水线不算成功。检查与 MR 对应的实际提交和流水线，不能借用无关提交的成功记录。

确定性门禁由 CI 执行；高风险变更在合并前安排专项 Review。第一版不增加“每个 MR 都必须通过 AI 判断”的硬门禁。

读取不到 GitLab 项目设置时，记录“未核验”，不能根据 YAML 推断设置已经生效。Review 任务无权修改分支保护或 CI 配置。

## 3. 第二层：Daily Incremental Architecture Review

将现有 `ce-ops3 Infra Review` 升级为 `ce-ops3 Daily Infra & Architecture Review`，保留每天 09:00。运行时区沿用现有任务的 `Asia/Tokyo`。

范围仍是 `Infra + Code Structure + Architecture Drift`，只 Review，不修改业务或工程源码，不提交、不 Push、不创建 MR。

### 3.1 Review 基线【修订】

通过 `mac-da-mcp` 读取 `~/repos/ce-ops3-platform`，先读取适用的 AGENTS / Rules，再获取最新 `origin/dev`，固定本轮目标 SHA。审查期间远端前进，不改变本轮目标。

```text
last_complete_review_sha → 本轮固定的 origin/dev SHA
```

增量不等于只看 diff：读取变更文件完整上下文、受影响的调用方、公开契约和测试，并对核心 Infra 做必要的一致性检查。

| 情况 | 处理 |
| --- | --- |
| 首次无状态 | 显式建立基线；记录实际覆盖、未覆盖和待审范围，不把目标 SHA 之前的历史默认为已审 |
| 审查和计划验证全部完成，但发现问题或检查失败 | 持久化证据和问题后，可以推进完成游标；问题继续跟踪 |
| 漏审、计划内必要验证无法执行、工具失败、超时 | PARTIAL / BLOCKED；保存进度，不推进完成游标 |
| 目标与上次完成 SHA 相同 | 不重复全仓审查；仅按需复核开放问题和未完成验证 |
| 旧 SHA 不存在或不是目标的祖先 | BASELINE_RESET_REQUIRED；保留旧状态，显式重建覆盖记录，不静默改为新目标 |

首次基线不能无限扩张为全仓深审：至少完成规则和工程入口梳理，登记历史模块清单、已审范围和历史待审项。只有该初始化计划完整完成且历史缺口已持久化后，才记录 baseline anchor；它不是“历史全仓通过”。后续 Daily 负责新增量，Weekly 轮换补历史覆盖。

具体状态、写入顺序、并发与隔离要求见附录 A。

## 5. Daily Review — Code Structure

新增一级 Review：

```text
Code Structure / Responsibility Boundary
```

重点不是目录形式，而是：

> 每一层是否承担自己应该承担的职责。

## 6. Controller 职责

Controller 负责 HTTP 边界：读取请求参数，接入认证、授权和校验，调用 Service / Use Case，并映射响应。

```text
Request → Guard / Pipe / 边界组件 → Controller → Service → Response
```

认证与参数校验优先通过项目已有边界组件接入，不要求每个 Controller 方法手写认证或重复调用 Schema。资源级、租户级等业务授权仍需在合适的业务边界保证，不能因为“路由有 Guard”就默认全部授权已完成。

需要重点审查：Controller 写 SQL 或直接操作 Drizzle、实现复杂业务状态机或领域计算、管理 Queue 生命周期、直接承担 Storage SDK 和复杂重试细节。

Controller 保持薄层，但不按行数机械判错。

## 7. Service 职责

Service 负责：

```text
业务 Use Case
业务规则
业务编排
状态变化
跨领域能力协调
```

例如：

```text
创建导出任务
↓
检查业务条件
↓
持久化
↓
提交 Queue
↓
返回业务结果
```

需要报警：

```text
Service 处理 Express Response

Service 拼 HTTP status

Service 到处解析 Header

Service 同时承担 DB 基础设施生命周期

Service 同时承担 HTTP / Storage / Queue 底层细节

一个 Service 承担大量完全不同的 Use Case
```

### 数据访问边界【修订】

简单数据访问允许放在 Feature Service；查询复杂、需要复用或存在明确独立变化边界时，再提取 Feature-owned 数据访问模块。不能因为 Service 直接使用 Drizzle 就自动判错，也不要求每个 Service 必须配一个 Repository。

Service 可以使用注入的 Queue / Storage 能力完成业务编排；这不等于自己管理连接池、SDK 初始化、底层重试或基础设施生命周期。

不因检查规则引入 BaseService、BaseRepository，或只做转发的 Manager / Handler / Adapter 链。

## 8. Feature 职责

业务能力优先归属：

```text
src/<feature>/
```

例如：

```text
event-log/
analytics/
abtest/
```

Feature 自己拥有：

```text
业务 Service
业务 Schema
业务数据库 Schema
业务数据库 Comments
业务错误
业务 Queue handler
业务测试
```

典型正确案例：

```text
analytics/
├── analytics.schema.ts
└── analytics-schema-comments.ts

abtest/
├── abtest.schema.ts
└── abtest-schema-comments.ts
```

而不是重新膨胀：

```text
db/schema.ts
```

### 示例不是实施状态【修订】

上述 Feature 名称与目录用于说明归属关系。Review 以仓库实际模块为准，不要求创建这些示例目录，也不强迫所有 Feature 复制同一套文件模板。

## 9. DB Infra 职责

```text
src/db/
```

负责数据库基础能力：

```text
Connection
Pool
Nest lifecycle
Drizzle instance
Schema aggregation
Comment aggregation
DB safety utilities
```

不负责具体领域定义。

正确：

```ts
export * from '../analytics/analytics.schema.js'
export * from '../abtest/abtest.schema.js'
```

错误：

```text
db/schema.ts

2000 行
Analytics
A/B Test
Event Log
CRM
User
...
```

### 聚合与装配例外【修订】

`db/schema.ts`、`db/schema-comments.ts` 是显式聚合入口：可以引用 Feature 对外暴露的数据库定义，但不得反过来拥有业务表定义、领域注释或业务逻辑。

Drizzle 实例初始化所需的 typed schema 装配也属于例外：允许数据库装配代码消费聚合后的 Schema；不允许连接池、通用 DB 工具依赖具体 Feature Service 或业务流程。

例外按实际职责判断，不按文件名放行。迁移执行目录保留历史 migration；纯文件拆分且数据库结构未变时，不要求生成空 migration。

## 10. Contracts 职责

`packages/contracts` 是跨边界契约。

原则：

```text
Zod Schema
↓
runtime validation
↓
z.infer
↓
TypeScript Type
```

Daily Review 检查：

```text
有没有 Schema + interface 双份维护

有没有 Controller 手写一份已经存在的 Response Type

有没有 API / Web 各维护一套相同类型

有没有 DTO 和 Zod Schema 表达完全相同的东西
```

优先保持：

> Schema 是事实源。

### 同一语义，才要求同一事实源【修订】

数据库模型、业务模型、HTTP 输入和输出属于不同边界，不强迫合成一套 Schema。不同边界允许显式映射；只对表达同一语义、确实应同步演进的定义检查重复维护。

Schema 存在转换时，区分输入与输出：输入用 `z.input`，输出用 `z.output` / `z.infer`。不能把转换后的类型当成原始请求输入。

共享契约不反向依赖数据库实现，不为了省映射把 ORM 对象泄露为公共协议。

## 11. Infra 职责

通用 Infra 包括 Database、Config、Queue、Storage、HTTP foundation、Logging、OpenAPI 与测试基础设施。

基本依赖方向：

```text
Feature → Infra
Feature → Contracts
```

基础能力不能依赖具体业务实现。以下装配入口可引用模块的公开定义：

```text
AppModule / 模块装配
路由装配
Schema / Comment 聚合
Drizzle typed schema 装配
明确的 Feature-owned adapter
```

装配入口只能完成注册、连接和聚合，不能借此承载业务规则。通用连接池、日志核心、底层队列和存储能力仍不能依赖 Feature Service 或内部业务流程。

第 9 节的 DB 聚合属于此处明确例外，不应同时被判为依赖越界。

## 12. Daily Review — Dependency Direction

检查依赖方向是否退化。

例如：

```text
packages/ui
× apps/web
× apps/api
× business feature

packages/contracts
× apps/*
× DB implementation

Feature A
× Feature B internal implementation

Web
× apps/api/src/*
```

跨 Feature 优先：

```text
Feature B public API
```

而不是：

```text
../../feature-b/internal/foo.ts
```

### Web 职责边界【修订】

页面负责路由级组织；组件以展示与明确交互为主；Hook 负责有实际复用或独立状态逻辑的能力；API 客户端统一网络协议与错误适配；状态管理区分本地界面状态与服务端数据。

不要求机械地每个组件配一个 Hook，不把所有逻辑都塞入全局状态，不允许通用 UI 依赖应用内部 Feature。检查是否出现重复请求封装、页面同时承担复杂协议转换和业务状态机、跨层共享可变单例等有证据的问题。

这些是新增审查准则，不代表当前 Web 已采用特定框架、状态库或查询库。

## 13. Daily Review — Complexity Drift

Daily 不做全面重构，只发现明显膨胀。

重点观察：

```text
突然变大的文件

突然变长的函数

constructor 注入越来越多

一个 Service 职责快速扩张

重复的 switch / mapping

重复 validation

重复 error mapping

新的 wrapper 层

新的 BaseXXX

新的 common/shared/utils
```

重点是发现趋势。

不是看到：

```text
文件 301 行
```

就机械要求拆分。

判断标准：

```text
是否存在多个独立职责
```

而不是：

```text
文件行数
```

## 14. Daily Review — Simplification Map

每日增量阶段只做：

```text
Simplification Candidate Detection
```

例如发现：

```text
本次新增 Helper A
仓库已有 Helper B
功能 80% 相同
```

报告：

```text
P2 Simplification Candidate

新增代码：
已有实现：
重复点：
建议：
```

但：

```text
不自动修改
```

### 去重与持久化【修订】

候选使用稳定 ID。每天复核时更新同一条记录，不因为行号变化或改名就重新编号。语法相似或“80% 相同”只能作为搜索线索，不能作为应合并的结论；需要证明语义、边界和变化方向一致。

记录首次 / 最近发现 SHA、规则、代码证据、可信度和状态。待确认的推断不能作为已确认缺陷。

## 15. 第三层：Weekly Codebase Simplification Review

新增独立任务 `ce-ops3 Weekly Simplification Review`，与每日任务分开。采用原方案建议的周日 10:00，时区 `Asia/Tokyo`。

Weekly 对应 Reduce：汇总 Daily 候选、去重、识别跨模块关系并安排有限范围的深审。

### 覆盖方式【修订】

```text
全仓模块与工程入口扫描
          ↓
本周变化 + 高风险模块深审
          ↓
其余模块轮换覆盖
          ↓
候选收敛 → 人确认 → 独立修复 / 简化
```

不承诺每周逐行深审全仓。记录模块清单、最近深审 SHA / 时间、本轮实际范围、未覆盖范围和剩余队列。大仓库或预算不足时优先高风险范围，其余明确留待下轮。

Weekly 有自己的完成游标与覆盖记录，不能直接推进 Daily 的增量完成游标。

## 16. Weekly Reduce 的目标

主要目标是评估并减少长期复杂度，关注 Duplication、Unnecessary Abstraction、Responsibility Fragmentation、Dead Code、Compatibility Residue、Over-engineering 和 Architecture Inconsistency。

Weekly 的直接产物是经过证据核实和去重的候选，以及建议处理顺序；候选被接受、改动完成并验证后，才能计为实际收益。

Bug 不是主目标，但发现明确的安全、数据或运行问题时必须报告，不能因为任务叫 Simplification 而忽略。

## 17. Duplication Review

寻找：

```text
重复函数
重复 helper
重复 Schema
重复 Type
重复 validation
重复 error mapping
重复 HTTP adapter
重复 DB query pattern
重复 Storage wrapper
```

但不是看到两段一样就抽象。

判断：

```text
重复是否稳定
边界是否相同
未来是否一起变化
```

三个条件满足才值得抽象。

## 18. Unnecessary Abstraction Review

AI 很容易生成：

```text
BaseService
BaseRepository
Manager
Coordinator
Handler
Factory
Adapter
Provider
Helper
Utils
```

Weekly Review 检查：

```text
它有没有真实消费者？

有没有隐藏复杂度？

有没有只是把一行代码转发出去？

有没有只为了“以后扩展”存在？
```

例如：

```text
Controller
↓
Service
↓
Manager
↓
Handler
↓
Repository
```

如果每层只做：

```ts
return next.call()
```

就是需要重点审查的对象。

### 不能仅按名称或转发层数判错【修订】

Provider / Adapter / Factory 等名字不是缺陷。短的转发层也可能承担依赖注入、权限、事务、协议隔离或可观测性边界；先确认其职责与消费者，再判断是否仅为空壳。

## 19. Dead Code Review

寻找：

```text
无引用 export

无消费者 helper

旧 compatibility function

已被新实现替代的 adapter

废弃 Feature Flag

旧 DTO

旧 Schema

旧 migration helper

无消费者 package API
```

只报告证据充分的候选项。

不要凭名字猜“可能没用”。

### 无引用不等于可删除【修订】

确认静态引用之外的 package exports、脚本入口、路由 / 依赖注入注册、动态加载、外部消费者和生成流程。历史 migration、snapshot 和回滚或兼容期限相关文件，不能因为应用代码未 import 就认定无用。

Review 只报告候选，不删除任何内容。证据不足时标记待确认。

## 20. Codebase Consistency Review

同一类问题应该大致采用一致方式。

例如：

```text
Feature A
Schema 在 feature

Feature B
Schema 在 db/

Feature C
Schema 在 random shared/
```

Weekly Review 应指出这种漂移。

再例如：

```text
API A
Zod validation

API B
手写 if

API C
class-validator
```

如果没有明确原因，就是一致性债务。

但：

> 一致性不是要求所有模块复制同样目录模板。

## 21. 文件拆分判断标准

不要采用：

```text
超过 300 行就拆
```

而采用：

```text
一个文件存在几个变化原因？
```

如果一个文件同时因为：

```text
HTTP 变化
DB 变化
业务状态机变化
Storage 变化
```

都会修改它，那么职责很可能混杂。

这是比行数更可靠的信号。

## 22. Simplification Candidate 输出

Weekly 与 Daily 共用稳定问题记录，最少包含：

```text
ID：稳定 ID，不随行号变化重新生成
分类：Defect / Simplification Candidate / Pending Verification
严重度：P0 / P1 / P2（按影响判断）
可信度：High / Medium / Low
范围与代码位置：路径 + 符号 + 当前行号
证据：当前 SHA、触发条件、调用链或命令结果
违反规则或增加复杂度的原因：
建议：删除 / 合并 / 下沉 / 上移 / 收敛 / 保持
预期收益与测量口径：
风险与验证方法：
首次发现 SHA / 最近确认 SHA：
状态：待确认 / 已接受 / 延后 / 已拒绝 / 已解决
处理人或关联任务：未知时留空，不代填
修复 MR 与验证结果：尚无时留空
```

“已拒绝”必须保留理由；没有新证据不每天重复上报。“延后”保留原因和复核条件。“已解决”必须有改动及验证证据，不以文件暂时没有出现在 diff 中作为解决依据。

可以提出最有价值的少量候选，不设凑数指标；缺少测量依据时，不编造减少的行数、层数或性能收益。

## 23. 第四层：Targeted Architecture Review

以下高风险变化原则上在合并前手动触发专项 Review，不等 Daily / Weekly：新增大型 Feature、数据库模型大调整、引入 Queue / Storage、认证授权改造、API Router 调整、跨 workspace 重构、大量 AI 生成代码或大型 Refactor。

例：Review Event Log Architecture、Review A/B Test Persistence、Review Authentication Boundary。

专项 Review 可深入业务上下文，但默认仍只 Review。范围由具体 MR / 变更确定，不自动扩展到无关业务。已合并后发现风险时可补做，但不能把事后审查描述成已完成合并前拦截。

## 24. Review Severity

严重度按实际影响、触发条件、范围和紧迫性判断，可信度单独记录。

| 等级 | 判断标准 |
| --- | --- |
| P0 | 有充分证据的紧急重大风险，例如正在发生或可直接触发的严重越权、广泛数据破坏或关键服务不可用，需要立即处置 |
| P1 | 有具体证据的重要正确性、可靠性或边界问题，例如可复现的关键门禁失效、会导致错误行为的契约漂移；需要尽快修复 |
| P2 | 有证据的可维护性问题、简化候选或较低影响缺陷；可安排处理 |

“职责越界”不自动等于 P1，“可能有安全问题”不自动等于 P0。先说明影响和证据，不能用问题名称代替评级。

无法确认影响、缺少复现或调用链证据时，归类 Pending Verification；不伪装成确定缺陷。可信度低不等于风险一定低，仍应给出最小验证方式。

## 25. 不应该报告的东西

为了防止 AI Review 变成噪声，不报告：

```text
纯个人风格偏好

为了“更优雅”增加抽象

没有实际收益的设计模式

没有证据的“未来可扩展性问题”

单纯因为文件长

单纯因为函数名字不喜欢

只有一次重复就要求公共化
```

### 控制重复噪声【修订】

不重复完整输出既有未变化问题；日常报告重点是新增、升级、已验证解决和当前阻塞。重要未解决风险可简要提醒，但沿用原 ID，不当成新问题刷屏。

## 28. 自动修改原则

Daily、Weekly 和 Targeted Review 默认只 Review。

```text
发现问题 → 提供证据与候选 → 人确认 → 独立修复 / Refactor Task
        → 单独分支或 worktree → MR 门禁 → 合并 → 复核
```

定时任务禁止修改源码、自动重构、commit、Push、创建 MR、修改 GitLab 保护规则。

“只 Review”不等于进程完全不产生文件：允许在任务自有的隔离运行目录生成依赖、构建产物、测试数据、报告和状态。不能污染开发工作区或业务环境。

通过 `mac-da-mcp` 访问本机；不可用时报告 BLOCKED，不改用 m1-mcp，不因此停用任务。安全和状态规则见附录 A。

```text
AI / Developer 生成代码
          ↓

          ↓

          ↓

          ↓
```

Daily / Weekly 使用共享的问题记录与互斥机制，但各自管理完成游标。审查完成、检查通过、问题已解决是三个不同状态。

## 30. 最终原则

整个体系只坚持几个核心原则：

```text
正确性
↓
职责清晰
↓
简单
↓
可维护
↓
开发体验
↓
扩展性
```

不是：

```text
抽象越多越专业
层越多越规范
文件越小越好
重复一点就提公共库
```

而是：

> 一个概念尽量只有一个事实源。

> 一个模块尽量只有清晰的变化原因。

> 属于业务领域的东西回到业务领域。

> 基础设施只承担基础设施职责。

> AI 快速扩张代码，人和 AI 一起周期性降低复杂度。

> 为未来保留扩展空间，但不提前实现未来。

本修订版用于配置 Daily 与 Weekly 的只读审查任务。配置成功不代表已读取仓库、完成首次基线或通过代码检查；这些必须由真实运行记录证明。

## 附录 A：执行协议 v1.1【新增】

这部分是本次提出的运行规则，不代表本地状态目录或隔离资源已经创建。

### A.1 访问与隔离

只用 `mac-da-mcp`。连接失败时输出 BLOCKED，保留定时任务启用状态，不改用 m1-mcp。先读实际仓库和适用规则，不根据记忆替代当前事实。

固定 `origin/dev` 目标，在任务自有的 detached worktree 内执行必要检查。安装或运行前查看脚本副作用。允许测试和构建生成文件，但不能修改源码、自动提交或创建 MR，也不能对开发 checkout 做 stash/reset/clean。

测试必须明确隔离 PostgreSQL、Storage、Queue，使用受限测试凭证；不得自动复制用户 `.env` 或输出密钥。不能确认测试资源安全时不运行相关命令，明确列为未执行。只清理本轮自有资源。

### A.2 持久化位置

建议第一版放在执行机器的用户状态目录，不写入源码仓库，不新建数据库或治理服务：

```text
~/.local/state/ce-ops3-platform/governance/
├── state.json
├── findings.json
├── lock/
└── runs/
    └── <run_id>/
        ├── report.md
        └── result.json
```

创建前先检查已有内容；不能覆盖未知格式、其他仓库的记录或不兼容协议。身份记录使用规范化仓库路径、移除凭证后的 remote 指纹与目标分支。报告不含密钥。

`state.json` 至少保存协议版本、仓库身份、Daily/Weekly 独立的最近完成 SHA、pending 范围、初始化历史缺口、Weekly 模块覆盖和最近运行 ID。`findings.json` 保存第 22 节的问题字段。`result.json` 保存本轮固定目标、覆盖、命令及状态，便于人工核验。

这些文件是执行进度和问题记录，不替代仓库 AGENTS / 架构决策；状态缺失不能用聊天记忆猜回 SHA。

### A.3 并发与写入顺序

Daily / Weekly 共用一个原子互斥锁，保护共享状态并避免重型测试冲突。锁记录本轮 ID 与执行身份；占用时返回 BLOCKED_CONCURRENT，不盲目抢锁或删除无法确认失效的旧锁。只有持有者能释放自己的锁。

写入顺序：本轮报告与证据 → 本轮 result → findings → state 游标。采用临时文件和原子替换，游标最后更新。某步失败时不推进游标，下次据已保存结果与稳定 ID 恢复，避免漏审或重复创建问题。

不承诺任务调度器天然提供代码级事务或跨主机锁。本规则面向同一台执行机器；多机同时执行不在第一版范围内。

### A.4 独立状态

| 状态维度 | 值 / 含义 |
| --- | --- |
| execution_status | COMPLETE：本轮计划审查与必要验证已执行且持久化完成；PARTIAL：部分完成；BLOCKED：未能开展 |
| findings_status | NONE / FOUND / PENDING_VERIFICATION |
| check_status | 每个命令独立记录 PASS / FAIL / NOT_RUN / NOT_APPLICABLE |
| finding lifecycle | 待确认 / 已接受 / 延后 / 已拒绝 / 已解决 |

检查执行失败不自动等于执行过程未完成；例如已复现测试失败、记录证据并完成剩余审查，可以 COMPLETE + FOUND + check FAIL。缺少环境导致必要检查无法执行则为 PARTIAL / BLOCKED。

游标只有在覆盖与计划内必要验证完成、结果成功保存后推进。可选或不适用检查必须事前解释范围，不能事后降低要求。首次 baseline anchor 明确携带历史缺口，不代表历史代码全部通过。

### A.5 运行验收

需要真实试运行验证以下行为，不能仅凭任务提示词认为已经可靠实现：

| 场景 | 验收结果 |
| --- | --- |
| 首次运行 | 固定目标，建立初始化覆盖，登记历史未审；只有完成初始化计划才保存 anchor |
| 新提交增量 | 覆盖完整变更及必要上下文，保存报告后推进 Daily 游标 |
| 测试失败 / flaky | 失败证据保留，复跑通过不抹去失败；是否审完与门禁是否通过分别展示 |
| 工具中断 / 必要验证缺失 | PARTIAL / BLOCKED，旧完成游标不变，pending 保留 |
| 无新提交 | 不重复全仓 Review，不把开放问题判为已解决 |
| 同时启动 | 一方持锁，另一方报告并发阻塞，不覆盖共享状态 |
| 历史改写 / 仓库身份不符 | 显式阻塞或重建基线流程，不静默跳过历史 |
| 问题重复 / 已拒绝 | 稳定 ID 去重，无新证据不重复报告 |
| 问题解决 | 记录修复与验证证据后才关闭 |
| mac-da-mcp 不可用 | 报阻塞，不停用任务，不声称已读仓库 |

只读任务不自行修复上述失败场景中的源码或工程配置。首次试运行完成后再根据真实误报、耗时与覆盖调整，不提前新增专用治理平台。
